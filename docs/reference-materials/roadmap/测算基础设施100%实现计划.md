### 0.2 100% 的真实定义

FateCat 达到 100% 时，必须同时满足：

- 对开发者：不读源码也能通过 OpenAPI、SDK 示例、sandbox、错误码和文档接入。
- 对 Agent：所有体系必须通过 capability registry 和 executor 调用，不能让模型自行重算或拼报告。
- 对使用者：报告结构稳定、免责声明稳定、隐私边界稳定、证据可追溯。
- 对审计者：数据、典籍、vendor、规则、测试、CI、发布证据可以逐项复核。
- 对运维者：health/ready/metrics/traces/logs/SLO/alerts/runbook/rollback 可用。
- 对发布者：local CI、远端 CI、container、SBOM、provenance、live smoke、rollback、clean git 全部可证明。

## 1. 调研结论

成熟基础设施产品的共性不是“功能多”，而是把复杂领域压成可发现、可执行、可审计、可观测、可回滚的稳定资源。

| 参考领域 | 官方依据 | FateCat 同构要求 |

| API 基础设施 | [OpenAPI Specification](https://spec.openapis.org/oas/latest.html) 定义 HTTP API 的标准、语言无关接口描述 | 对外 API 必须有机器可读契约、错误码、schema、示例和版本策略 |
| 支付 API | [Stripe Idempotent requests](https://docs.stripe.com/api/idempotent_requests) 使用幂等键避免重复副作用 | 报告 job、记录写入、callback 必须支持幂等、防重复和参数一致性校验 |

## 2. 目标终态

FateCat 100% 测算基础设施应具备五层架构：

```text
Client / Agent / Web / Bot / CLI / Skill
  -> Delivery Surface / API Contract / Auth
  -> Capability Control Plane
  -> Calculation Job / Durable Runtime
  -> Provider Adapter / Mature Engine / Data Source
  -> Evidence Builder / Report Builder
  -> Evaluation / Observability / Security / Supply Chain Gates
```

终态原则：

- 所有体系都是 `Capability`，不能绕过 registry 执行。
- 所有生产能力都有 `Provider`，不能靠散落函数和前端拼接。
- 所有长流程都是 `CalculationJob`，不能依赖单进程内存完成生产可靠性。
- 所有报告都是 `Report`，JSON/Markdown/profile/evidence/policy gate 同源。
- 所有结论必须能追溯 evidence，不允许 LLM 或模板凭空编造依据。
- 所有质量判断必须来自 golden、snapshot、benchmark、CI、smoke 或真实外部连通证据。
- 所有外部资料和开源仓必须有 manifest、license/usage status、provenance 和导出边界。

## 6.8 2026-07-04 W2 Certification Current Release Proof Bridge

W2 runtime proof pack 推送后，发现 certification aggregator 存在一个证据时间线盲区：`local-ci` 产物里的 `current-release-proof.json` 生成时间早于最终远端 release proof；而最终 release proof 不能写回 Git，否则会制造新的 HEAD，导致证明再次变旧。

本切片的正确解法不是复制 release proof 逻辑，也不是把 live release gate 改成 passed，而是给 certification aggregator 增加显式 sidecar 输入：

```bash
bash scripts/measurement-infrastructure-certification.sh \
  --evidence-dir <local-ci-output-dir> \
  --current-release-proof-json <current-release-proof.json> \
  --output-json <path>
```

语义边界：

| Evidence | Source | Override | Effect |
| --- | --- | --- | --- |
| `current-release-proof.json` | sidecar 可选 | 允许 | 代表当前 HEAD 的远端 CI、container、digest、attestation 和 rollback dry-run 证明。 |
| `live-release-gate.json` | local-ci evidence dir；0115 后可独立 sidecar | 0113 时不允许；0115 后独立允许 | 继续代表生产 API/HF/Bot 等外部 live 交付条件；无真实证据时仍可阻断 release domain。 |

验收口径：

- summary 必须记录 `evidenceOverrides`。
- evidence item 必须记录 `logicalPath`、`path` 和 `source`。
- sidecar 通过时，`current-release-proof.json` 可以显示 passed/override。
- 若 `live-release-gate.json` 仍 blocked，release domain 必须继续 blocked；0115 后即使用 current live gate sidecar，blocked 语义也不变。
- 该桥接不代表 FateCat 已达到 100% 测算基础设施，只代表 certification 能准确引用当前发布证明。

## 6.9 2026-07-04 W2 Certification Current Audit Bundle Bridge

## 6.11 2026-07-04 W2 External Validation Closure Plan Gate

0115 后，certification 可以引用当前 live gate、release proof 和 audit bundle sidecar，但 current audit bundle 里的 `pending-external-validations.json` 仍只是 occurrence 清单：它能证明“哪里写了外部连通验证待执行”，但不能告诉审计或交付负责人“谁负责、需要什么凭证、跑什么命令、什么证据才算关闭”。

基础设施同构资料给出的共同模式是：OpenAPI/AsyncAPI/CloudEvents 把接口和事件变成机器可读 contract，Kubernetes controller 把 desired/current 状态变成可 reconciliation 的对象，Backstage 把 Component/API/Resource 纳入 catalog，SLSA/CycloneDX 把发布证据和组件清单变成可校验证据。FateCat 对应的下一步不是把外部验证项写成自然语言 TODO，而是把它们变成可分派、可关闭、可门禁的 closure plan resource。

本切片新增 `contracts/fate/audit/external-validation-closure.json` 与 `scripts/external-validation-closure-gate.sh`：

```bash
bash scripts/external-validation-closure-gate.sh \
  --pending-external-json <pending-external-validations.json> \
  --output-json <external-validation-closure-gate.json>
```

语义边界：

| Resource | Source | Effect | Non-claim |
| --- | --- | --- | --- |
| `pending-external-validations.json` | current audit bundle | 输入 occurrence 清单。 | 只证明有待验证项，不证明 live。 |
| `external-validation-closure-gate.json` | 0116 gate output | 为每个 occurrence 生成 category、owner、credentialDependencies、requiredEvidence、verificationCommands、closureCondition。 | 只生成关闭计划，不连接真实 API/Bot/Postgres/OIDC/SIEM/OTel/Vault/KMS/developer portal/第三方审计系统。 |
| `shipGate.status` | closure gate policy | 有任何 pending item 时保持 `blocked`。 | 不能把计划写成 production passed 或 audit passed。 |

验收口径：

- 每个外部待验证 occurrence 必须有 owner、凭证依赖、required evidence、复核命令和关闭条件。
- 无法自动分类的 occurrence 必须进入 `manual_triage`，不能静默丢弃。
- 输出不得包含 token、secret、password、数据库 URL、DSN 等敏感赋值形态、私钥或真实生产日志正文。
- `local-ci` 必须在 current audit bundle 之后运行该 gate，并把 artifact 路径写入 `summary.json`。
- 该 gate 不减少 `externalPending` 数量；它只把待验证项从“散落文本”提升为“可关闭计划”。
