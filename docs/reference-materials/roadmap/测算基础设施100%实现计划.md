## 1. 调研结论

成熟基础设施产品的共性不是“功能多”，而是把复杂领域压成可发现、可执行、可审计、可观测、可回滚的稳定资源。

| 参考领域 | 官方依据 | FateCat 同构要求 |
| --- | --- | --- |
| API 基础设施 | [OpenAPI Specification](https://spec.openapis.org/oas/latest.html) 定义 HTTP API 的标准、语言无关接口描述 | 对外 API 必须有机器可读契约、错误码、schema、示例和版本策略 |
| 支付 API | [Stripe Idempotent requests](https://docs.stripe.com/api/idempotent_requests) 使用幂等键避免重复副作用 | 报告 job、记录写入、callback 必须支持幂等、防重复和参数一致性校验 |
| 持久工作流 | [Temporal Durable Execution](https://docs.temporal.io/evaluate/understanding-temporal) 把长流程状态交给平台保存和恢复 | 长报告、多 provider 组合、批量评测要从内存任务升级为可恢复状态机 |
| 重试策略 | [Temporal Retry Policies](https://docs.temporal.io/encyclopedia/retry-policies) 将重试声明化 | provider 外部依赖、webhook、评测 runner 需要声明式 retry/timeout/non-retryable policy |
| 软件目录 | [Backstage System Model](https://backstage.io/docs/features/software-catalog/system-model/) 用 Component/API/Resource 建模系统 | Capability、Provider、Dataset、EvaluationRun、SecurityControl、DeliverySurface 必须可发现 |
| 控制面 | [Kubernetes Controllers](https://kubernetes.io/docs/concepts/architecture/controller/) 通过 desired state/current state reconciliation 管理资源 | FateCat 需要 admission gate、status、ready、policy gate，而不是散落 if/else |
| Provider 生态 | [Terraform Providers](https://developer.hashicorp.com/terraform/language/providers) 把外部能力插件化、版本化、锁定化 | 八字、紫微、黄历、梅花等 provider 必须声明来源、版本、健康、许可证和能力边界 |
| 可观测性 | [OpenTelemetry Signals](https://opentelemetry.io/docs/concepts/signals/) 统一 traces、metrics、logs | API -> job -> provider -> report builder 必须能串起 trace、metrics、structured logs |
| SRE | [Google SRE SLO](https://sre.google/sre-book/service-level-objectives/) 用 SLO/error budget 管理可靠性 | 需要 p95/p99、错误率、队列积压、provider failure rate、release budget |
| 供应链安全 | [SLSA v1.2](https://slsa.dev/spec/v1.2/) 用 levels、provenance、attestation 改进供应链安全 | 需要 release provenance、SBOM、vendor/source/license/data manifest、artifact verification |
| API 安全 | [OWASP API Security Top 10 2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/) 明确 BOLA、认证、资源消耗、配置、库存等风险 | 记录接口、管理接口、callback、provider 外部调用必须有 RBAC、限流、审计和 API inventory |
| ML 平台 | [MLflow Model Registry](https://mlflow.org/docs/latest/ml/model-registry/) 强调版本、lineage、治理和生产切换 | 测算规则、provider、报告 profile、golden dataset 应有版本、lineage、promotion gate |

结论：FateCat 的 100% 不是把六爻、奇门、大六壬全部堆进去，而是让每个测算体系进入同一套能力协议、provider 生命周期、证据模型、评测门禁和生产运行控制面。

## 2. 目标终态

FateCat 100% 测算基础设施应具备五层架构：

```text
Client / Agent / Web / Bot / CLI / Skill
  -> Delivery Surface / API Contract / Auth
  -> Capability Control Plane
  -> Calculation Job / Durable Runtime
  -> Provider Adapter / Mature Engine / Data Source
  -> Evidence Builder / Report Builder
  -> Evaluation / Observability / Security / Supply Chain Gates
```

终态原则：

- 所有体系都是 `Capability`，不能绕过 registry 执行。
- 所有生产能力都有 `Provider`，不能靠散落函数和前端拼接。
- 所有长流程都是 `CalculationJob`，不能依赖单进程内存完成生产可靠性。
- 所有报告都是 `Report`，JSON/Markdown/profile/evidence/policy gate 同源。
- 所有结论必须能追溯 evidence，不允许 LLM 或模板凭空编造依据。
- 所有质量判断必须来自 golden、snapshot、benchmark、CI、smoke 或真实外部连通证据。
- 所有外部资料和开源仓必须有 manifest、license/usage status、provenance 和导出边界。

没有这些证据时统一写：`外部连通验证待执行`。
