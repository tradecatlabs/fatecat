# 性能基线与优化路线

> 最近复核：2026-07-13。性能优化必须先证明正确性和 hot path，不以无界并发或静默降级换取表面速度。

## 当前基线

`scripts/core-performance-smoke.sh` 在开发机对八字、紫微各执行一次预热和三次采样，默认单次预算 2000 ms。当前观测均值约为：八字 464 ms，紫微 121 ms。该数据只用于提交间回归，不代表生产 p50/p95/p99，也不能推导公共服务容量。

## 立即保持

1. quick CI 保留轻量性能 smoke，超过预算直接失败并保存 JSON 证据。
2. 生产请求记录 capability、阶段耗时、成功/失败类型和队列等待时间，但不得记录出生资料或报告正文。
3. 所有 vendor 子进程保持明确 timeout、退出码与结构化错误；核心计算失败时返回失败，不生成半完整报告。
4. 进程内报告队列保持容量、TTL 和并发上限；Telegram 降级不得阻塞 Web/API readiness。

## 需要测量后再做

| 候选优化 | 触发证据 | 验证方式 | 风险 |
|---|---|---|---|
| 把同步计算移入受限线程池 | 事件循环阻塞使 API p95 超预算 | 并发 1/4/8 压测、event-loop lag、CPU 与内存峰值 | GIL、vendor 线程安全、线程池耗尽 |
| 长驻 Node worker | iztro 子进程启动占紫微耗时主要比例 | 分阶段 profiling 与 100 次 warm benchmark | 进程生命周期、协议和恢复复杂度 |
| 结果缓存 | 相同规范化输入重复率足够高 | 命中率、节省 CPU、敏感数据留存审计 | 隐私、缓存键、失效和跨用户泄露 |
| 外部任务队列 | 多副本或任务恢复成为真实需求 | 队列等待 p95、重试率、恢复演练 | 新基础设施、幂等与运维成本 |
| 异步数据库驱动 | DB 写入进入请求 hot path | 查询计划、连接池等待、写入 p95 | 迁移成本和事务语义变化 |

## 暂不执行

- 不直接对所有同步函数机械套 `asyncio.to_thread()`；先通过 event-loop lag 和并发压测证明收益。
- 不并行执行存在数据依赖的命理阶段；错误依赖图会破坏可复现性。
- 不在没有命中率和隐私策略时引入报告缓存。
- 不做自动预热真实命盘；如需预热，只使用固定测试输入且不持久化。
- 不把模块失败降级成“部分成功报告”，除非 capability 契约明确允许并能标明完整性状态。

## 生产验收指标

上线前至少记录：冷启动耗时、单请求与并发 4/8 的 p50/p95/p99、吞吐、event-loop lag、CPU、RSS 峰值、子进程次数、队列等待、超时率和错误率。任何优化都应以相同输入集做前后对照，并保留回滚路径。
