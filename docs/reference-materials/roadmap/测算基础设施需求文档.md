# FateCat 测算基础设施需求文档

> 状态：Draft
> 用途：定义 FateCat 作为“测算基础设施”应具备的产品、工程、数据、治理和交付需求。
> 边界：本文是需求文档，不是任务容器，不承诺所有需求已经实现。

## 1. 背景

FateCat 当前已经具备综合八字、紫微斗数、黄历择日、梅花易数等能力入口，并开始形成统一 capability 协议、API、Web、Bot、Skill、多端交付和 evidence 字段。

但如果项目目标提升为“测算基础设施”，它就不能只停留在“能排盘、能生成报告”。基础设施的核心是：让 Agent、应用开发者和后续业务系统可以稳定、可重复、可审计地调用测算能力，并能在能力升级、供应链变化、报告格式变化、外部部署变化时保持可控。

参考成熟基础设施产品的同构规律：

- Stripe 把支付变成标准 API、幂等请求、Webhook、测试模式和审计事件。
- Twilio 把通信变成消息资源、状态回调、错误码和渠道抽象。
- Plaid 把金融数据连接变成 Link、Sandbox、Webhook 和数据产品。
- Kubernetes 把运行环境变成声明式资源、controller、ready 状态和 reconciliation。
- Terraform 把云资源变成 provider、resource、data source、plan/apply/state。
- Temporal 把长流程变成可恢复工作流、队列、重试和状态机。
- OpenTelemetry 把系统运行变成 trace、metric、log 三类可观测数据。

FateCat 要做的是同构地把“测算能力”变成：

- 标准能力资源；
- 稳定 API 契约；
- 可复现计算；
- 证据化解释；
- 可观测执行；
- 可评测质量；
- 可治理供应链；
- 可多端交付。

## 2. 项目定位

FateCat 是面向 Agent 与应用开发者的测算基础设施，提供统一的能力协议、可复现计算核心、证据化解释层和多端交付接口。

它不是：

- 单一八字排盘工具；
- 单一网页测算站；
- LLM 直接脑补命理结论的 Prompt 集；
- 多个术数模块的简单堆叠；
- 未经测试的玄学功能集合。

它应该是：

- 可被应用和 Agent 接入的测算 API；
- 可被审计的计算与解释系统；
- 可持续接入八字、紫微、黄历、梅花、六爻、奇门等 provider 的能力平台；
- 可把传统术数计算、资料、规则、报告、风险边界统一管理的基础设施。

## 3. 目标用户

| 用户 | 需求 |
| --- | --- |
| 应用开发者 | 通过 API 调用测算能力，拿到稳定 JSON、Markdown、状态、错误和证据 |
| Agent 开发者 | 通过 capability 协议选择能力，不让模型自行重算或编造规则 |
| 内容产品 | 生成结构稳定、可复制、可导出的报告 |
| 运维人员 | 部署服务、观察健康状态、排查错误、控制限流和凭证 |
| 审计人员 | 复核数据源、算法来源、规则证据、隐私治理和测试结果 |
| 后续能力开发者 | 按 provider 模板接入新体系，而不是破坏默认报告 |

## 4. 总体目标

### 4.1 业务目标

- 让综合八字和紫微成为两个生产级 capability 样板。
- 让黄历、梅花等独立体系通过 capability 接口使用，不混入默认综合八字报告。
- 为六爻、奇门、大六壬、风水九星、姓名合婚等未来体系提供统一接入协议。
- 让报告输出具备稳定结构、清晰免责声明、隐私边界和证据链。

### 4.2 工程目标

- 所有能力通过统一 capability registry 登记。
- 所有生产能力通过统一 executor 执行。
- 所有生产能力拥有输入契约、输出契约、证据契约、风险契约和测试门禁。
- 所有多端入口复用同一计算与报告链路。
- 所有对外入口具备健康检查、ready 检查、metrics、错误码、限流和日志。

### 4.3 质量目标

- 生产能力必须可复现、可回归、可审计。
- 关键历法、节气、起运、真太阳时、紫微盘面等边界必须有 golden 回归。
- 报告结构必须有 snapshot 或结构回归。
- 示例数据不得暴露真实用户或真实非北京地区。
- 外部生产验证必须明确区分“本地已验证”和“外部连通验证待执行”。

## 5. 资源模型需求

FateCat 应把测算能力抽象成稳定资源，而不是散落函数。

| 资源 | 含义 |
| --- | --- |
| `Capability` | 一个可登记、可发现、可准入、可执行或被拒绝的测算能力 |
| `Provider` | 某个 capability 的计算实现来源，可以是项目内 usecase、成熟开源库或外部服务 |
| `CalculationJob` | 一次同步或异步计算任务 |
| `Report` | 面向用户或 Agent 的输出报告，支持 JSON / Markdown |
| `Evidence` | 支撑结论的规则、数据源、盘面、权重、冲突和边界 |
| `Dataset` | 历法、典籍、规则、golden 命例、外部 benchmark 等数据资产 |
| `EvaluationRun` | 一次回归、benchmark 或质量评测运行 |
| `UserRecord` | 可选持久化记录，必须有权限、脱敏和关闭机制 |

## 6. 功能需求

### 6.1 Capability Registry

| 编号 | 需求 |
| --- | --- |
| REQ-CAP-001 | 系统必须维护统一 capability registry，记录能力 ID、名称、传统体系、状态、可见性、输入、输出、provider、风险和成熟度 |
| REQ-CAP-002 | capability 状态至少包括 `planned`、`experimental`、`production` |
| REQ-CAP-003 | `planned` 能力必须不能执行，只能用于路线登记和接口预留 |
| REQ-CAP-004 | `production` 能力必须声明 `testGate.status=passing` 和至少一个本地回归入口 |
| REQ-CAP-005 | 默认 Markdown 能力必须且只能是 `bazi`，其他体系必须独立输出 |
| REQ-CAP-006 | registry 变更必须由测试覆盖，错误配置必须在 ready 或测试阶段失败 |

### 6.2 Provider 标准

| 编号 | 需求 |
| --- | --- |
| REQ-PROV-001 | 每个生产 capability 必须绑定一个明确 provider |
| REQ-PROV-002 | provider 必须声明 engineVersion、deterministic、输入要求和证据策略 |
| REQ-PROV-003 | provider 应优先复用成熟库、稳定开源仓库或已登记供应链资产 |
| REQ-PROV-004 | 自研代码只允许承担编排、适配、结构化、证据化和报告表达 |
| REQ-PROV-005 | provider 失败必须返回标准错误，不得吞掉异常后输出伪成功 |

### 6.3 API 与开发者接入

| 编号 | 需求 |
| --- | --- |
| REQ-API-001 | 系统必须提供 `/metadata`，用于服务发现、入口发现、质量门禁和隐私口径 |
| REQ-API-002 | 系统必须提供 OpenAPI 契约，至少覆盖 capability、report、health、ready、metrics |
| REQ-API-003 | 系统必须提供 `/capabilities` 列出能力状态、成熟度、测试门禁和风险策略 |
| REQ-API-004 | 系统必须提供 `/capabilities/{capability_id}/calculate` 执行生产能力 |
| REQ-API-005 | 系统必须提供 `/reports` 暴露报告 profile 和 job 入口 |
| REQ-API-006 | API 响应必须包含稳定 `success`、`data`、`error`、`metadata` 或等价字段 |
| REQ-API-007 | API 必须支持明确错误码和 HTTP 状态码映射 |

### 6.4 幂等、异步任务与回调

| 编号 | 需求 |
| --- | --- |
| REQ-JOB-001 | 长报告生成应支持异步 job |
| REQ-JOB-002 | job 状态应统一为 `queued`、`running`、`succeeded`、`failed`、`expired`、`cancelled` |
| REQ-JOB-003 | 对外 API 应支持幂等键，避免重复提交生成重复报告 |
| REQ-JOB-004 | 未来可支持 webhook/callback，让调用方接收报告完成事件 |
| REQ-JOB-005 | job 失败必须保留错误类型、requestId 和可排查摘要 |

### 6.5 报告系统

| 编号 | 需求 |
| --- | --- |
| REQ-REP-001 | 默认报告只输出综合八字，不自动混入紫微、黄历、梅花、六爻等体系 |
| REQ-REP-002 | 报告必须支持 JSON 和 Markdown 两类输出 |
| REQ-REP-003 | Markdown 结构必须可测试、可复制、可快照回归 |
| REQ-REP-004 | 报告必须包含免责声明，不得输出确定性恐吓断语 |
| REQ-REP-005 | 报告应保留 evidence 引用，而不是只给自然语言结论 |
| REQ-REP-006 | 多端入口不得自行拼装核心报告块，必须复用统一 profile 或 report builder |

### 6.6 Evidence 与解释层

| 编号 | 需求 |
| --- | --- |
| REQ-EVI-001 | 生产能力输出必须包含 evidence 或 metadata 中的 evidencePolicy |
| REQ-EVI-002 | 关键结论应能追溯到 ruleId、source、basis、盘面字段或计算路径 |
| REQ-EVI-003 | 多规则冲突时必须表达冲突点、主规则、辅助规则和保留意见 |
| REQ-EVI-004 | 神煞、称骨、民俗建议等辅助体系不得影响八字核心喜忌和格局判断 |
| REQ-EVI-005 | 无法确认来源的结论不得伪装成古籍依据 |

### 6.7 数据与知识资产

| 编号 | 需求 |
| --- | --- |
| REQ-DATA-001 | 历法、节气、典籍、规则、命例、供应链仓库必须有明确存放位置和 manifest |
| REQ-DATA-002 | 原始大文件、版权不确定资料、运行态产物不得混入生产导出包 |
| REQ-DATA-003 | 典籍文本进入规则层时应转成结构化索引，不应在报告中大段复制原文 |
| REQ-DATA-004 | 节气、真太阳时、起运等关键数据必须有 golden 样本和来源说明 |
| REQ-DATA-005 | 外部资料必须区分可生产使用、仅研究参考、版权待复核、禁用 |

### 6.8 评测与回归

| 编号 | 需求 |
| --- | --- |
| REQ-EVAL-001 | 每个 L3/L4 capability 必须有回归测试 |
| REQ-EVAL-002 | 八字必须覆盖节气边界、真太阳时、月令、起运、格局、用神和报告结构 |
| REQ-EVAL-003 | 紫微必须覆盖十二宫、主星、辅星、四化、命身宫、运限和典型格局 |
| REQ-EVAL-004 | 系统必须保留匿名 golden 命例，不得使用真实用户隐私样例 |
| REQ-EVAL-005 | 规则升级必须能对比升级前后输出差异 |

### 6.9 可观测性

| 编号 | 需求 |
| --- | --- |
| REQ-OBS-001 | 服务必须提供 `/health`、`/ready`、`/metrics` |
| REQ-OBS-002 | 每次请求必须有 requestId |
| REQ-OBS-003 | 日志必须结构化，包含 route、status、elapsedMs、errorClass |
| REQ-OBS-004 | metrics 至少覆盖请求量、错误量、延迟、并发槽、队列状态 |
| REQ-OBS-005 | 未来应支持 trace，把一次报告从 API 到 provider 到 report builder 串起来 |

### 6.10 安全与隐私

| 编号 | 需求 |
| --- | --- |
| REQ-SEC-001 | 生产记录接口必须有 token 或用户级权限 |
| REQ-SEC-002 | 日志、文档、测试、前端示例不得输出真实 token、secret、DSN、私钥 |
| REQ-SEC-003 | 公开 Web 示例和用户界面不得展示北京以外的真实地区名称 |
| REQ-SEC-004 | API 必须有请求体大小限制、限流和并发保护 |
| REQ-SEC-005 | 所有外部连通验证必须标明是否真实执行 |
| REQ-SEC-006 | 免责声明必须覆盖娱乐参考、非科学确定性、非医疗法律金融建议 |

### 6.11 多端交付

| 编号 | 需求 |
| --- | --- |
| REQ-DEL-001 | Web、API、Bot、CLI、Skill 必须复用统一核心计算与报告链路 |
| REQ-DEL-002 | Web 端应支持体系切换，但默认只输出综合八字 |
| REQ-DEL-003 | Bot 端应支持异步队列、用户限流和失败提示 |
| REQ-DEL-004 | Skill 入口应能安装、预检、执行、导出、验收 |
| REQ-DEL-005 | 所有渠道输出的同一 profile 应保持结构一致 |

### 6.12 供应链与复用

| 编号 | 需求 |
| --- | --- |
| REQ-SUP-001 | 成熟开源库、稳定工具、权威资料优先于自研底层算法 |
| REQ-SUP-002 | 第三方仓库必须进入 reference 或 vendor 管理区，不得污染生产路径 |
| REQ-SUP-003 | 每个 provider 应记录依赖来源、版本、用途、许可证复核状态 |
| REQ-SUP-004 | 导出包不得包含 raw、缓存、运行态 DB、vendor build 产物 |
| REQ-SUP-005 | vendor health 和 source hygiene 应进入发布门禁 |

## 7. 非功能需求

| 类别 | 需求 |
| --- | --- |
| 正确性 | 关键计算必须可复现，边界样本必须回归 |
| 稳定性 | API 契约不得随意破坏，新增字段优先兼容 |
| 性能 | 同步请求必须有超时、并发槽和请求体上限 |
| 可维护性 | 新体系必须按 capability/provider/profile 接入 |
| 可审计性 | 结论、数据源、规则、测试和门禁必须可追溯 |
| 可移植性 | Skill 导出包应能脱离开发仓库运行基础能力 |
| 可观测性 | 运行状态、错误、延迟和队列必须可见 |
| 隐私 | 示例、日志、报告、记录接口必须遵守脱敏边界 |

## 8. 成熟度定义

| 等级 | 名称 | 要求 |
| --- | --- | --- |
| L0 | registered | 只登记，不执行 |
| L1 | prototype | 可本地 demo，不能进入生产 API |
| L2 | integrated | 接入 executor，有基础 schema 和 smoke |
| L3 | validated | 有 regression、golden、evidence、privacy、source hygiene |
| L4 | production | 多端同源输出，门禁通过，可审计交付 |

## 9. 100% 基础设施验收口径

FateCat 达到“测算基础设施 100%”时，应满足：

1. 能力全部资源化：所有体系都通过 capability registry 管理。
2. 执行全部统一化：生产能力只通过统一 executor 执行。
3. 契约全部稳定化：输入、输出、错误、证据、风险都有 schema。
4. 计算全部可复现：provider、engineVersion、determinism、golden 可查。
5. 解释全部证据化：关键结论可追溯 ruleId/source/basis。
6. 交付全部同源化：Web/API/Bot/CLI/Skill 不自行拼核心结果。
7. 运行全部可观测：health、ready、metrics、日志、requestId 可用。
8. 发布全部门禁化：quick CI、acceptance、privacy、source hygiene、vendor health、export smoke 可执行。
9. 隐私全部默认安全：公开示例、日志、报告、记录接口不泄露敏感数据。
10. 外部生产全部实测：真实域名、CORS、token、Bot live smoke、生产部署链路有证据。

## 10. 当前能力与差距

| 领域 | 当前状态 | 主要差距 |
| --- | --- | --- |
| capability registry | 已有基础字段、成熟度和准入规则 | 仍需完整 input/output/error/evidence schema |
| executor | 已有统一 executor 和 provider map | 需要更标准的 provider interface |
| API | 已有 `/metadata`、`/capabilities`、`/reports`、OpenAPI | 需要资源详情、标准错误码、幂等键、callback |
| 报告 | 综合八字默认、紫微独立，部分体系 standalone | 需要报告 snapshot 和 profile schema 更强 |
| evidence | 已开始规则 ID 和 evidencePolicy | 需要规则索引覆盖更完整，冲突解释更系统 |
| eval | 已有部分回归和 golden | 需要更大命例集、紫微典型盘、边界 benchmark |
| observability | 已有 health/ready/metrics/requestId | 需要 trace、provider 级指标、报告级审计链 |
| privacy | 已有前端地区展示限制和扫描门禁 | 需要全链路脱敏测试、日志脱敏规则和白名单 |
| supply chain | 已有 vendor/source hygiene | 需要许可证分级、provider 依赖 manifest 和更新策略 |
| production | 本地门禁较完整 | 真实生产域名、token、Bot live smoke 仍待执行 |

## 11. 明确不做

- 不把所有术数体系混在一个默认报告里。
- 不让 LLM 自行重算四柱、紫微盘或起卦。
- 不用自然语言解释替代结构化计算结果。
- 不把 planned 能力说成 production。
- 不为了功能数量降低测试、证据、隐私和供应链要求。
- 不在无法确认版权或来源时把资料包装成生产可用规则。

## 12. 术语

| 术语 | 含义 |
| --- | --- |
| capability | 一个可登记、可发现、可执行或可拒绝的测算能力 |
| provider | capability 背后的计算实现 |
| profile | 报告输出结构和展示契约 |
| evidence | 支撑结论的证据链 |
| golden | 用于锁定边界行为的标准样本 |
| sandbox | 可供开发者测试的非真实用户环境 |
| production gate | 发布前必须通过的质量、安全和运行门禁 |
