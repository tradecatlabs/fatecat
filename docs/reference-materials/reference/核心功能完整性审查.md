# 核心功能完整性审查

> 日期：2026-07-13
> 范围：综合八字、紫微、capability 执行器、分发闭包、Web/API/Bot 交付面和生产边界。

## 结论

综合八字与紫微已经是两个独立 production capability。Web、API、Bot 和 CLI 共用 `CapabilityExecutor`，delivery 不再选择 legacy/capability 双引擎；核心内部仍通过适配器复用遗留 `BaziCalculator` 与成熟 vendor，这是实现细节而不是第二条公开生产路径。

当前仓库具备本地复用、回归和审计能力，但不能直接宣称“公开分发与完整生产 100%”：公开 Skill 包受上游许可证阻断，真实 HF/Telegram/外部数据库连接、专家命例评审和生产 SLO 仍需外部证据。

## 生产与分发边界

| 项目 | 状态 | 原因或处理 |
|---|---|---|
| wheel 独立执行综合八字/紫微计算 | 未完成 | vendor 引擎未打入 wheel；当前 wheel 定位为协议、资源和编排包 |
| 内部 lite Skill 运行 | 可验收 | 明确包含所需 vendor 运行闭包，并执行体积、文件数与卫生门禁 |
| 公共 Skill 分发 | 阻断 | `bazi-1`、`sxwnl` 缺少可确认的上游分发许可证；`--public` 门禁必须拒绝 |
| HF Space live | 外部连通验证待执行 | 最终提交部署后验证 `/health`、`/ready`、`/metrics`、`/web` |
| Telegram live | 外部连通验证待执行 | 需要真实 token、webhook 注册与 Telegram API |
| 专业命理准确性 | 外部评审待执行 | golden 能防回归，不能替代专家盲评、外部 benchmark 和 no-leak 签字 |

## 剩余核心缺口

1. 将八字、紫微的大型规则实现继续拆成可独立测试的 kernel/provider，但保持 capability 与报告契约不变。
2. 扩充匿名命例、节气/真太阳时边界和规则冲突反证 corpus，并接入真实外部 benchmark runner。
3. 为公开分发取得许可证证明，或替换为许可证清晰且结果经过 golden 对齐的引擎。
4. 把进程内报告任务升级为可选持久队列后，才能讨论多副本、高并发和可靠任务恢复。
5. 在真实生产环境补齐 CORS、token、网关限流、日志/指标、Bot webhook 与部署回滚证据。

## 禁止回潮

- 非八字体系统不得混回综合八字默认报告。
- Web/API/Bot 不得各自重新实现排盘或报告规则。
- 神煞、称骨等辅助规则不得覆盖月令、旺衰、格局、调候和用神主线。
- 本地通过不得被描述为外部 live、专家审核、许可证授权或生产 SLO 通过。
